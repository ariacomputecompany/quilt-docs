`AMP` is a curated application surface that runs inside Quilt-managed infrastructure.

Like the other tooling pages, the point is not that AMP happens to use containers underneath. The point is that Quilt can host the application as a real, isolated service environment for end users.

GitHub: [ariacomputecompany/amp](https://github.com/ariacomputecompany/amp)

## What AMP Is For

- application-specific workflows that should run in a stable isolated environment
- repeatable sessions that users can launch without manual infrastructure assembly
- deployment on Quilt infrastructure with the same operational model as other curated tools

## Why It Matters In Quilt

AMP matters because it represents the product layer on top of Quilt's runtime primitives.

Quilt gives the platform:

- isolated execution
- OCI-backed environment delivery
- networking and access primitives
- durable session and lifecycle behavior

AMP gives the user-facing application experience that rides on those primitives.

## Mental Model

Use AMP when the user intent is:

- launch the application
- work inside the curated environment
- let Quilt own the infrastructure boundary

That is different from using Quilt as a generic container toolbox.

## Where It Fits

| Need | Better choice |
|------|---------|
| Focused application environment hosted by Quilt | AMP |
| Raw runtime operations and container semantics | Quilt runtime docs |
| Cluster, node, and workload orchestration | `quiltc` |

## Used Through Quilt Nightly

AMP is typically surfaced through `quilt-nightly`, which launches the curated environment for the user on top of Quilt infrastructure.

This page keeps the focus on AMP itself. The launcher UX can evolve independently without changing why AMP belongs in the Quilt tooling model.
